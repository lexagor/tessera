The problem

Why agent deals stall in security review.

Logs are self-asserted. IAM says who the agent is, not what it actually did on whose authority.

01

Which agent acted, and for which human?

Attribution has to survive the handoff from a human session to an autonomous tool call.

02

What exact call was authorized?

The tool, arguments, intent, and policy version need to be bound together — not reconstructed from logs.

03

Which credential did it receive?

Short-lived and scoped is not enough if the reviewer cannot see what was issued, for how long, and for what.

04

What happened, and can it be checked?

An audit trail a third party can verify offline is different from a dashboard only the vendor can inspect.

How it works

Enforce. Bind. Verify. Prove.

One execution path from policy decision to portable evidence.

  1. 01

    Enforce

    Evaluate per-action policy and issue a scoped credential — or a broker-held grant the agent never sees.

  2. 02

    Bind

    Sign the agent, human authority, intent, policy hash, tool definition, argument hash, credential thumbprint, and outcome.

  3. 03

    Verify

    Check the record offline with the open-source verifier. No call back to Tessera and no trust in the vendor.

  4. 04

    Prove

    Share a verification page or an exportable evidence pack mapped to the controls a reviewer asks for.

agent.tspolicy: allow
const call = await tessera.authorize({
  tool: "stripe.refunds.create",
  intent: "refund a duplicate charge",
  args: { charge: "ch_123", amount: 4200 },
  authorityToken,
});

if (call.decision === "allow") {
  await tessera.proxy({
    grantId,
    argsHash: call.credential.argsHash,
  });
}

The proof

A receipt, not another log line.

A signed record binds the authorization decision and the outcome into one artifact. Change one signed field and verification fails.

Human→Intent→Policy→Agent→Tool→Credential→Outcome→Signature
Level 1 · broker-observed

Argument-bound execution

The broker holds the provider credential, re-checks the exact argument hash at execution time, forwards one request, and signs the observed response.

Example: Stripe broker-held grant
Level 2 · scoped credential

Provider-scoped access

The broker authorizes a scoped credential and signs the authorization plus the agent-reported outcome. The provider, not Tessera, enforces its scope.

Examples: AWS STS, GitHub, OAuth bearer
Caller-asserted

No authority artifact

The principal is supplied by the caller. The record proves what the broker recorded, not that an IdP authenticated the delegation.

Security posture

Built for the reviewer, not just the demo.

Precise claims, explicit limitations, and evidence a third party can check.

Human authority

OIDC session → short-lived delegation token → broker-verified hmac-jwt. Tenant/agent scoped, issuer/audience checked, replay-protected, and rotation-aware.

Tenant isolation

Per-environment broker keys, separate receipt chains, cross-tenant tests, and optional Postgres RLS for shared databases.

Custody and verification

EIP-712 signatures, hash-linked chains, optional on-chain anchors, a KMS/HSM signing bridge, and an open-source offline verifier.
